# Проект прогнозирования оттока клиентов

Проект представляет собой ML-систему для прогнозирования вероятности оттока клиентов и формирования целевого сегмента пользователей с повышенным риском отсутствия транзакции. Архитектура построена как набор из двух микросервисов с разделением ответственности: один сервис отвечает за внешний доступ и управление пользовательским взаимодействием, второй — за работу модели, batch-сегментацию и offline-оценку качества.

## Цель проекта

Цель проекта — помочь бизнесу заранее выявлять пользователей с высокой вероятностью снижения активности и использовать эту информацию для удерживающих сценариев. Система позволяет не только оценивать риск для отдельного пользователя, но и формировать приоритетный список клиентов для последующих маркетинговых действий.

## Бизнес-ценность

Проект ориентирован на повышение точности работы с клиентским оттоком. Использование модели позволяет:

- концентрировать внимание на сегменте повышенного риска;
- снижать долю нерезультативных коммуникаций;
- использовать ресурсы удержания более адресно;
- формировать ранжированный сегмент пользователей для дальнейшей работы маркетингового контура.

Таким образом система поддерживает как индивидуальную оценку риска, так и сценарий массового отбора пользователей для целевого воздействия.

## Основные сценарии использования

В проекте реализованы два базовых сценария:

- получение единичного прогноза по пользователю через REST API;
- формирование batch-сегмента пользователей с наибольшей вероятностью оттока.

Первый сценарий подходит для интеграции с внешними приложениями и сервисами. Второй — для подготовки списка пользователей, которых нужно отсортировать по риску и передать дальше в бизнес-процесс удержания.

## Что делает система

Система принимает подготовленные признаки пользователя, рассчитывает вероятность оттока и возвращает:

- индивидуальный риск пользователя;
- итоговую метку по бизнес-порогy;
- ранжированный список пользователей для целевого сегмента `Top-N%`.

Таким образом проект поддерживает два основных сценария:

- `online`-сценарий — получение единичного предсказания через API;
- `batch`-сценарий — формирование списка пользователей с максимальным риском оттока для маркетингового воздействия.

## Состав проекта

### `gateway-service`

`gateway-service` — внешний вход в систему. Он:

- принимает запросы от клиента;
- создаёт пользовательскую сессию;
- сохраняет пользовательскую сессию в PostgreSQL;
- валидирует доступ;
- проксирует запросы в `inference-service`.

Этот сервис нужен для того, чтобы пользователь не работал с моделью напрямую. В нём сосредоточены HTTP-вход, работа с токеном сессии, хранение сессий в `PostgreSQL` и взаимодействие с сервисом инференса.

### `inference-service`

`inference-service` — сервис модели. Он:

- загружает LightGBM-модель из `S3`-совместимого хранилища;
- считает вероятность оттока;
- преобразует score в бизнес-метку;
- формирует ранжированный целевой сегмент;
- содержит offline-блок обучения и оценки модели.

Именно этот сервис отвечает за ML-логику проекта.

## Архитектурный подход

Оба сервиса организованы в стиле `Clean Architecture`. Это означает, что код разделён на несколько уровней ответственности:

- `domain` — сущности и бизнес-правила;
- `application` — сценарии использования;
- `infrastructure` — технические адаптеры;
- `interfaces` — API и схемы обмена данными.

В `inference-service` дополнительно выделен блок `training`, который отвечает за офлайн-обучение, offline-оценку и расчёт метрик качества модели.

Общий интерфейс конфигурации вынесен в `config/config.py`. Через него сервисы получают значения переменных окружения: порты, `S3`-URI модели, threshold, сетевые настройки и строку подключения к базе данных.

## Как работает логика проекта

### Онлайн-сценарий

1. Клиент обращается в `gateway-service`.
2. `gateway-service` создаёт сессию и сохраняет её в `PostgreSQL`.
3. Запрос передаётся в `inference-service`.
4. `inference-service` загружает модель и рассчитывает вероятность оттока.
5. Вероятность сравнивается с порогом `threshold`.
6. Пользователь получает JSON-ответ с числовым score и итоговой меткой.

### Батчевый сценарий

1. В `inference-service` передаётся список пользователей с признаками.
2. Для каждого пользователя рассчитывается вероятность оттока.
3. Пользователи сортируются по убыванию риска.
4. Формируется сегмент заданного размера, например `Top-20%`.
5. На выходе получается таблица:
   - `user_id`
   - `probability_of_inactivity`
   - `rank`

## Модель и данные

В проекте используются подготовленные датасеты:

- `data/processed.csv` — выборка для обучения;
- `data/test_data.csv` — выборка для offline-проверки качества.

В этих файлах каждая строка соответствует одному пользователю, а колонки представляют собой уже агрегированные признаки:

- статистики по операциям за весь период;
- признаки по окнам `last3m` и `last1m`;
- временные признаки активности;
- поведенческие признаки;
- целевую переменную `churn`.

Основная модель проекта хранится в `S3` по URI вида `s3://ml-artifacts/models/lgb_model.joblib`.  
Дополнительно в том же хранилище сохраняется `baseline_logreg.joblib` как базовая модель для сравнения с основной LightGBM.

## Офлайн-оценка качества

В проекте реализован отдельный offline-блок оценки качества модели.  
Он нужен не для runtime API, а для проверки того, насколько хорошо модель ранжирует пользователей по риску.

Сейчас рассчитываются метрики:

- `ROC-AUC`
- `Precision@Top Share`
- `Lift@Top Share`

Результаты offline-обучения и оценки также сохраняются в `S3`, например по URI `s3://ml-artifacts/reports/training_metrics.json`.

## Хранилище артефактов

Артефакты модели в проекте больше не зависят от локальной файловой системы контейнера.

- `inference-service` загружает production-модель из `S3`;
- `train.py` сохраняет основную модель, baseline-модель и отчёт с метриками напрямую в объектное хранилище;
- `evaluate.py` читает модель для offline-проверки тоже напрямую из `S3`;
- для локального и стендового запуска в `docker-compose.yml` поднят `MinIO` как `S3`-совместимое хранилище.
- при старте `docker-compose` отдельный контейнер `artifact-trainer` обучает модель и публикует артефакты в `S3`, поэтому `inference-service` не зависит от локальной папки с моделями.

## База данных

Для постоянного хранения сессий в проект добавлен `PostgreSQL`.

- `gateway-service` использует таблицу `user_sessions`;
- при создании сессии сервис сохраняет `user_id`, `token` и время создания;
- при запросе на предсказание валидность токена проверяется уже не в памяти процесса, а в базе.

## Развёртывание

Проект разворачивается через `docker-compose.yml`.  
В контейнерную конфигурацию уже включены оба микросервиса, `PostgreSQL`, `MinIO` и их сетевое взаимодействие:

- `postgres` поднимается как хранилище пользовательских сессий;
- `minio` поднимается как `S3`-совместимое хранилище артефактов модели;
- `artifact-trainer` публикует модель и отчёты в `S3` перед запуском `inference-service`;
- `gateway-service` поднимается как внешний REST-вход;
- `inference-service` поднимается как внутренний ML-сервис;
- модель подключается по `S3`-URI;
- параметры запуска берутся из `config/config.py` и переменных окружения.

### Как выполняется деплой

1. В корне проекта запускается сборка контейнеров.
2. Docker собирает отдельные образы для `gateway-service` и `inference-service`.
3. После сборки контейнеры поднимаются в одной сети через `docker-compose`.
4. `gateway-service` начинает обращаться к `inference-service` по внутреннему адресу контейнера и использовать `PostgreSQL` для сессий.

Команда развёртывания:

```bash
docker compose up --build
```

### Что доступно после запуска

- `gateway-service` — внешний API проекта на порту `8000`
- `inference-service` — внутренний API модели на порту `8001`
- `postgres` — БД для хранения пользовательских сессий на порту `5432`
- `minio` — `S3`-совместимое хранилище артефактов на портах `9000` и `9001`

Основные сценарии после деплоя:

- через `gateway-service` можно создать сессию и получить единичное предсказание;
- через `inference-service` можно получить batch-сегментацию пользователей по риску оттока;
- через `inference-service` можно проверить техническое состояние сервиса по `health` endpoint.

Таким образом деплой поднимает сразу полную рабочую схему проекта: входной сервис, ML-сервис, `PostgreSQL`, `S3`-совместимое хранилище артефактов и модель, подключённую к inference-слою.

## Проверка качества кода

В проект добавлены `flake8` и `mypy` для статической проверки кода.

Проверка `gateway-service`:

```bash
cd services/gateway-service
python -m flake8 src tests
python -m mypy --config-file mypy.ini
```

Проверка `inference-service`:

```bash
cd services/inference-service
python -m flake8 src tests
python -m mypy --config-file mypy.ini
```
